# Electron 插件生命周期服务 v1

本文记录 `electron/plugin-lifecycle.ts`、`electron/plugin-trust-store.ts` 和 `electron/plugin-ipc.ts` 的职责和运行边界。该实现属于 P5 隔离试点。桌面设置页通过受限 IPC 使用生命周期服务；Web 版本不加载外部插件。

## 操作流程

1. `installArchive()` 调用签名包安装器。它验证包签名、API 兼容范围、ZIP 条目和文件哈希，再把静态资源暂存到调用方提供的安装根目录。安装不会执行插件脚本。
2. `listInstalled()` 扫描安装根目录，并验证每个 `plugin.json` 的签名和 API 版本。清单无效的包会以 `invalid` 状态返回。此步骤不读取每个资源文件的完整内容。
3. `activate()` 在启动窗口前重新检查插件身份、签名、目录内容和每个受签名保护文件的 SHA-256。它拒绝额外文件、缺失文件、符号链接、硬链接、特殊文件和越界目录。
4. 宿主传入本次激活的能力授权。授权必须同时属于插件清单的请求范围和当前宿主支持的范围。当前服务支持 `runtime.info`、`clipboard.write`、`settings.read` 与 `settings.write`。清单可以保留已知但暂未实现的能力声明；沙箱启动时会过滤这些声明，不会把它们交给能力代理。
5. 每个插件 ID 同时只运行一个版本。激活新版本时，服务先销毁旧窗口，再打开新窗口。新窗口启动失败时，服务会重新验证旧版本并尝试恢复。
6. `disable()` 销毁该插件的活动窗口。`uninstall()` 会在必要时先停用插件，然后只删除安装根目录内指定版本的目录。其他已安装版本保留。

## 插件版本的浏览器会话

沙箱用插件 ID 和解析后的安装目录计算非持久 Electron Session 分区。每个已安装版本使用独立分区。该规则让新版本启动失败后，旧版本可以在自己的 Session 中恢复，也避免插件版本共享浏览器存储。

外部插件的持久化设置由宿主通过 `window.itTools.capabilities.settings` 提供。设置保存到宿主用户数据目录的版本 1 JSON 文件，按插件 ID 分区，不复用插件 Session 的 `localStorage`。因此设置可以跨已安装版本、回滚和应用重启使用。接口只接受非秘密的字符串、有限数字、布尔值和 `null`，并限制键、值、条目数和文件大小。它不提供凭据、文件或网络存储。

## 签名信任与桌面管理界面

`PluginTrustStore` 将受信任的 Ed25519 公钥、密钥 ID 和允许的插件 ID 保存到 `<userData>/plugins/trusted-keys.json`。它只保存规范化公钥，不保存私钥。存储更新使用同目录临时文件和重命名。读取会拒绝符号链接、硬链接、无效 JSON、重复密钥 ID 和超出大小限制的文件；错误时不会清空或覆盖原数据。

全局 `/settings` 页的“Electron 插件包”区显示插件包和签名者管理项。旧地址 `/settings/extensions` 会重定向到该页面。用户先粘贴公钥并查看 SHA-256 指纹，再通过系统确认对话框信任该密钥。密钥必须列出允许签名的插件 ID。安装使用 Electron 文件选择器；主进程不会把本机包路径返回到渲染器。启用时，用户可以选择清单已请求且宿主支持的能力，主进程再次显示这些能力并取得确认；已知但暂未实现的能力只显示为不支持，不提供授权选项。撤销签名密钥前，主进程先停止使用该密钥的所有活动插件。

桌面 IPC 只接受主框架和受信任应用来源。插件窗口没有 preload，因此不能调用这些 IPC。Web 界面显示外部插件包仅支持 Electron 的说明。签名信任与能力授权分开执行，能力只在当前插件窗口期间有效。

## 限制和失败处理

- 安装包上限为 128 个插件版本，同时最多运行 4 个插件窗口。
- 插件包路径最多有 32 个段。该限制也控制启用前的目录检查量。
- 插件入口必须在 15 秒内加载。服务每 2 秒向渲染器发送一次固定的 `executeJavaScript('void 0')` 探测。单次探测 10 秒内没有完成或返回错误时，服务会销毁插件窗口。Electron 报告窗口无响应 10 秒后，服务也会销毁窗口。`render-process-gone` 事件会立即触发销毁。
- 插件窗口必须在 5 秒内关闭。超时会使停用、升级或卸载失败，避免服务错误报告插件已退出。
- 插件关闭会触发沙箱清理并撤销本次窗口的能力授权。授权不跨应用重启保存。
- 服务不会在应用启动时自动运行已安装插件。插件必须由后续管理界面明确启用。设置文件不会在启动时主动加载插件代码。
- 应用允许用户导入其验证过的发布者公钥，但仓库没有内置生产签名密钥或受维护的插件包。
- 新版本失败后，若旧版本文件或签名也已损坏，服务会报告 `activation-rollback-failed`，并保持插件停止。

## 验证

`electron/plugin-lifecycle.test.ts` 覆盖签名包安装、启用前完整性检查、能力授权、活动插件数量上限、版本启动失败后的恢复、无响应探测超时、渲染器退出事件，以及停用活动窗口后按版本卸载。`electron/plugin-settings-store.test.ts` 覆盖设置文件的命名空间、并发写入、损坏处理和资源上限。`electron/plugin-manager.e2e.spec.ts` 验证签名者信任、包安装、拒绝和授予能力、跨版本设置读取、升级失败恢复旧版、同步无限循环插件被关闭、宿主设置页继续响应、撤销活动插件的签名者与卸载。包签名和 ZIP 安全边界由 `electron/plugin-package.test.ts` 另行覆盖。

无限循环验证由 Windows Electron 自动化测试运行。该测试还调用 Electron `forcefullyCrashRenderer()` 终止插件渲染进程，并确认插件窗口从主进程窗口列表移除、宿主设置页仍可用、已安装包仍保留。该自动化不代替人工真实窗口验收，也不覆盖自然发生的 Chromium 崩溃或 Linux/macOS 行为。
