# IT Tools 主线路线：Web/Electron 产品承载与 Ramag 场景互补

> 状态：现行路线
> 更新日期：2026-10-25
> 执行入口：[01-development-plan.md](01-development-plan.md)
> P0 边界记录：[14-cross-project-capability-matrix.md](14-cross-project-capability-matrix.md)
> 适用范围：Web/PWA、Electron、与 Ramag 的功能边界、性能和插件扩展

## 1. 路线目标

it-tools-template 是 Web/PWA 和 Electron 产品所有者。它负责通用工具、数据库管理器、
系统监控、桌面工作台、桌面分发和插件管理。ramag-platform 独立负责少量需要 Rust/GPUI
原生能力的场景。两个项目不共享进程、运行时、代码包或接口协议，只在功能边界和用户场景上互相参照。

## 2. 接收范围

| 优先级 | 产品范围 | it-tools-template 的交付 | Ramag 的处理 |
|---|---|---|---|
| P0 | 数据库和普通系统监视 | 完成三引擎工作台、采样、分页、编辑、取消和清理 | 停止新增 GPUI 功能，准备移除重复工具 |
| P1 | API、Git、对象存储、容器 | 完成 Electron 页面、连接状态、历史和权限边界 | 仅保留迁移所需兼容期 |
| P2 | Redis、MongoDB、Kafka、MQTT | 完成协议操作、消息/文档结果、取消和错误恢复 | 移除对应工具入口和基础设施依赖 |
| P2 | 剪贴板、更新和普通系统能力 | 由 Electron 主进程统一管理权限、托盘和分发 | 不再维护第二套产品流程 |
| P3 | 纯计算工具和 JSON Path | 统一 Web、Electron 和 WASM 入口及测试样例 | Ramag 可独立选择高收益工具，不建立调用关系 |
| P4 | SSH/SFTP/PTY、隧道和 Ramag 私有安全能力 | 当前不纳入 it-tools-template 主线 | 由 Ramag 独立实现和发布 |

## 3. 接入顺序与停止条件

1. 先建立功能矩阵。每项记录唯一所有者、平台、数据边界、权限、取消、资源上限、旧入口和回滚版本。
2. 先完成 Electron 替代流程，再从 Ramag 删除导航、默认构建和专用路线。
3. 能由浏览器、Web Crypto、WASM、Electron 主进程或现有插件能力完成的功能，优先留在 it-tools-template。
4. Ramag 只在 Electron 实现成本高、收益低或原生能力明显更强时独立开发。
5. 两个项目的功能相似时，只记录场景差异和产品所有者，不建立调用关系。

以下条件会暂停下一项迁移：关键操作缺失、错误/取消/权限不一致、凭据或配置迁移风险、
资源预算未满足，或两个仓库出现同一业务逻辑的第二份实现。

## 5. 与性能和插件路线的关系

原有 P0–P5 性能、任务执行器、工具定义、第一方 SDK 和 Electron 插件工作继续作为
it-tools-template 的技术支线。它们服务于本产品的工具承载和扩展，不推动 Ramag 扩大工具范围。
插件只能使用 it-tools-template 自己声明和授予的能力；它不能加载 GPUI 或调用 Ramag 的进程。

## 性能与插件支线：保留的技术主线

建议向“可扩展的本地开发者工具平台”发展。执行顺序是：建立性能基线、优化现有工具、统一扩展接入、交付第一方插件，再验证第三方插件的隔离与分发。

当前工具组件已有懒加载、统一注册和共享路由，适合演进为模块化工具包。第三方运行时代码还缺少隔离、资源限制、权限检查和升级恢复，因此只能作为后续试点。第一阶段的模块化就能降低新增工具成本，不必等待插件商店完成。

| 扩展形态 | 可行性判断 | 建议时机 |
| --- | --- | --- |
| 内置工具模块与构建时工具包 | 高；当前注册结构可渐进迁移 | P3 |
| 项目维护的第一方插件，随应用构建和审查 | 较高；需要 SDK、生命周期和兼容检查 | P4 |
| 用户安装的独立插件包 | 有条件可行；需要独立运行环境及安装管理 | P5 试点 |
| 公开第三方插件商店 | 暂无足够工程证据和维护能力 | P5 验收后另行排期 |

“第一方插件”指本项目审查并维护的代码；“第三方插件”指来源与应用不同、应按不可信代码处理的扩展。包签名用于确认来源和完整性，不能证明代码安全。

### P1 第二片结果：OUI 数据按需加载

`oui-data@1.2.0` 已改为构建依赖。生成脚本从 MA-L、MA-M、MA-S 三份注册表读取 53,542 条记录，并按 MAC 前缀自适应生成 38 个 JSON 分片。最大分片为 186,685 字节 gzip（约 182.31 KiB），全部分片原始数据共 5,482,755 字节。生成文件带内容哈希名称，并写入版本清单。生成器只清理自己命名的旧分片，保留目录中的其他文件。

查询先读取同源版本清单，再读取与 MAC 前缀匹配的一个分片。查询按 MA-S 9 位、MA-M 7 位、MA-L 6 位的顺序匹配。数据请求设有大小与 10 秒超时限制；地址不离开当前应用。请求失败时显示重试操作，失败请求不保留在内存缓存。MAC 地址不完整或格式错误时不请求数据。

Web 与 PWA 只在使用 MAC 查询工具后获取清单和所需分片。Service Worker 将已读取的清单及分片放入运行时缓存；更新 ID 现在按资源路径和内容计算，因此同一路径上的数据变化会替换旧运行缓存。离线时仅保证已缓存分片可用。Electron 构建将完整生成数据随应用打包，运行时仍只解析所需分片。BSD-2-Clause 来源说明随数据生成，并保存在[许可证文件](licenses/oui-data-BSD-2-Clause.txt)。

### P2：避免大输入阻塞，并能真正停止任务

- 正则匹配、正则样例生成、Text Diff、JSON minify、CSV to JSON、CSV to Markdown、JSON to CSV、JSON Lines、JSON/XML/YAML/TOML 转换、SQL 格式化、Environment Variables Parser、Bcrypt 哈希/比较、Markdown 转 HTML、Docker Run 转 Compose、List Converter、IPv4 CIDR Merge、IPv4 CIDR Overlap Checker 和 IPv4 CIDR Containment Checker 已迁移到任务执行器。cURL Code Generator 保持同步执行，输入最多 256 KiB、最多 16,000 个解析 token、生成输出最多 2 MiB；页面只生成当前所选格式，并将请求头和警告表限制为各 500 行。已有合成输入基准不足以支持 Worker 迁移。其他同步解析工具仍待评估。
- Worker 请求携带任务 ID、输入版本和输出上限。输入变化会终止旧任务，新任务在 150 ms 防抖后启动。Worker 超时由宿主终止，旧版本结果不会写回页面。
- 每个渲染器最多运行两个任务；每个工具最多保留一个最新等待任务。这个限制适用于当前 Electron/Web 渲染器，不跨多个 Electron 窗口共享。
- 正则输入最多 256 KiB、模式最多 4,096 字符、结果最多 5,000 项、输出最多 1 MiB、匹配最多运行 1 秒。Text Diff、JSON minify、CSV to JSON 和 JSON to CSV 的输入最多 256 KiB、输出最多 2 MiB、任务最多运行 10 秒；Text Diff 另限制合计 20,000 行。
- XML 格式化、XML/JSON 互转和 YAML/JSON 互转的输入最多 256 KiB、输出最多 2 MiB、任务最多运行 10 秒。XML 格式校验和转换都在 Worker 内运行，避免校验先在页面线程解析大输入。
- Worker 和页面离开时取消的任务都会终止对应 Worker。后续仍需验证 Worker、监听器和媒体资源在连续切换 20 轮后的计数与回收。
- TOML 的 JSON、YAML 双向转换已迁入共享 Worker。其余大输入工具仍需逐项设定字节、行数和输出上限。确需整体载入的算法要先检查大小；批量文件再评估流式处理。
- SQL Formatter 使用独立 Worker，避免把 `sql-formatter` 加入共享 Worker；输入最多 256 KiB，输出最多 2 MiB，运行最多 10 秒。Environment Variables Parser 使用共享 Worker，一次解析后同时返回诊断与所选格式；输入最多 256 KiB、2,000 行，输出最多 2 MiB，运行最多 10 秒。
- Bcrypt 哈希与比较使用独立 Worker；盐轮数限制为 4–16，合并输入最多 64 KiB，输出最多 4 KiB，任务最多运行 5 秒。
- Docker Run 转 Compose 使用独立 Worker；输入最多 256 KiB，结构化结果最多 2 MiB，任务最多运行 10 秒。Text Statistics 通过一次字符循环统计字符、词和行数，避免为词数和行数分配分割数组。
- List Converter 使用独立 Worker；输入最多 1 MiB、最多 100,000 行，输出最多 2 MiB，任务最多运行 10 秒。Worker 在调用转换器前计算文本、包装选项和分隔符的输出上界；预计结果超过上限时直接返回限制状态。
- IPv4 CIDR Merge 使用独立 Worker；输入最多 256 KiB、最多 32,768 行，序列化输出最多 2 MiB，任务最多运行 10 秒。Worker 一次完成解析、校验和合并，并逐项限制 CIDR 输出。
- IPv4 CIDR Overlap Checker 使用独立 Worker；输入最多 256 KiB、最多 1,000 行，结果最多包含 500 个重叠对，序列化输出最多 2 MiB，任务最多运行 10 秒。超过重叠对上限时不返回部分报告。
- IPv4 CIDR Containment Checker 使用独立 Worker；两份输入合计最多 256 KiB、1,000 行，结果最多包含 500 条匹配，序列化输出最多 2 MiB，任务最多运行 10 秒。超过匹配上限时不返回部分报告。
- 小输入不盲目转移线程；比较线程启动和复制成本。只有性能分析证明收益后，才为个别算法评估 WASM 或原生实现。

验收：正常输入输出与旧实现一致；高成本小正则和大文件都能超时或取消；旧任务不会覆盖新结果。连续切换代表工具 20 轮后没有逐轮累积的 Worker、监听或媒体资源，内存快照解释保留对象。Worker 可改善响应性，但仍可使用部分网络 API，不能单独充当第三方插件权限隔离；相关限制见 [MDN Worker 说明](https://developer.mozilla.org/en-US/docs/Web/API/Web_Workers_API/Using_web_workers)。

先以已有工具重组样例，再为每类增加一个小功能，验证真正的接入成本。数据提供器为工具供应结构化数据，首批使用 OUI 与协议参考资料。

SDK v0 的边界：

- PluginManifest 包含命名空间 ID、插件版本、宿主 API 兼容范围、平台入口、贡献项和能力请求；工具 ID 与插件 ID 一起解析，防止覆盖内置工具。
- 使用声明式激活条件，仅在打开工具、执行命令或读取对应数据时加载实现。闲置插件不能占用常驻 Worker 或主动轮询网络。
- 激活创建的资源归插件所有，停用必须释放。动态 import 的模块代码不保证从 JavaScript 缓存卸载；清理状态与资源、终止独立运行环境分别验证。
- 插件使用公开主题变量、翻译和组件接口，不直接修改宿主全局状态。宿主 API 使用独立的语义化版本，不依赖应用的日期加短哈希版本；API 变化提供兼容范围、弃用说明与迁移样例。
- SDK 先作为仓库内接口验证，达到稳定需求后再决定是否拆分独立包或 pnpm workspace。

验收：三个样例使用相同 SDK；重复激活/停用、缺失依赖、插件错误与宿主升级都有确定结果。故障插件可以停用，其他工具继续工作。受信任同进程代码仍可能造成宿主故障，因此该阶段不宣称提供第三方安全隔离。

### P5：独立插件包试点与进入条件

扩展宿主与宿主 UI 分离的设计可参考 [VS Code Extension Host](https://code.visualstudio.com/api/advanced-topics/extension-host)。本文借鉴职责分离，不承诺兼容 VS Code 插件或完整复制其架构。

| 平台与来源 | 执行方式 | 能力边界 |
| --- | --- | --- |
| Web/Docker 内置、第一方包 | 构建时纳入依赖图，运行时按需激活 | 浏览器支持的 API 和现有站点权限 |
| Electron 第一方包 | 优先沿用浏览器能力，系统操作通过受限适配器 | 每个原生操作有明确参数、来源检查和失败行为 |
| Electron 独立插件包试点 | 独立、开启 sandbox 的渲染环境；按插件隔离来源与 session | 不继承主窗口 preload、存储或媒体授权；宿主代理执行有效授权操作 |
| Web 独立插件包 | P5 先验证托管与隔离方案，不承诺本地 ZIP 直接安装 | 需要独立来源的 sandbox iframe 或受控计算环境；受 CSP、CORS 和浏览器能力限制 |

Vite 的 glob 导入在构建阶段转换，不能直接作为任意运行时插件加载器，见 [Vite 功能说明](https://vite.dev/guide/features#glob-import)。Web 扩展也不能默认获得 Node.js 能力，相关限制参考 [VS Code Web Extensions](https://code.visualstudio.com/api/extension-guides/web-extensions)。

试点实施范围：

1. 首选由项目维护的独立样例包，通过 Electron 本地安装验证完整流程。插件包包含已构建资源；安装时不运行脚本、不执行 `npm install`。
2. 校验包身份、API 范围、文件哈希和来源签名；限制解包总大小、文件数和压缩比，拒绝路径越界与符号链接逃逸。
3. 采用独立来源、独立 session、严格 CSP 和受限消息通道，分别验证存储、网络、窗口创建与下载行为。限制插件实例与子 Worker 数量，监测失去响应的运行环境并能独立终止。Worker 不是进程隔离；普通 Node 子进程或 `utilityProcess` 也不能直接用来运行不可信代码。
4. Capability Broker 同时检查宿主管理的插件身份、调用帧/来源、参数结构和有效授权，并限制消息大小与频率。只为用户选中的文件发放受限句柄；权限撤销或插件停用后，旧请求与句柄失效。
5. 网络能力由宿主按目的地址、方法、请求与响应大小控制；验证插件不能绕开代理直连。不会为浏览器端提供无边界的通用网络代理。iframe 的 sandbox 与 Worker 自身 CSP 都需单独验收。
6. 管理安装、启用、停用、升级、回滚和卸载。升级先写入暂存目录并校验，激活成功后切换；失败保留旧版本，设置按插件命名空间迁移。日志只记录操作状态，不记录用户文件内容或秘密。
7. 通过跨插件读取、越权文件访问、未授权外联、伪造消息、无限计算、崩溃和错误包安装的攻击样例。只有隔离验证通过，才扩大到第三方包。

Electron 保持 context isolation、进程 sandbox、导航限制和 IPC 来源检查；不能将通用 Electron API 暴露给插件。依据见 [Electron 安全指南](https://www.electronjs.org/docs/latest/tutorial/security)。通过签名校验不替代上述运行时检查。

验收：桌面独立插件故障后宿主仍可操作并能停用插件；插件不能读取宿主存储、其他插件数据或未经授权的文件。Web 不具备的能力有清楚的降级结果；Web 独立插件隔离若未通过，继续提供构建时工具包。

#### P5 第一片：Electron 沙箱渲染器原型（2026-10-18）

新增 `electron/plugin-sandbox.ts`，使用 `it-plugin://<pluginId>/` 作为插件来源。每个插件 ID 使用独立、非持久 Session。插件窗口不加载 preload，并开启 `nodeIntegration: false`、`contextIsolation: true`、`sandbox: true` 和 `webSecurity: true`。插件的 CSP 默认拒绝资源，只允许同源脚本、样式、图片、字体和 Worker；`connect-src` 不允许网络请求。Session 同时拒绝 HTTP、HTTPS、WebSocket、FTP、权限请求和下载。宿主也拒绝插件窗口的新窗口与外部导航。静态文件复用已存在的真实路径、符号链接和目录越界检查；单个资源最大 16 MiB。

Electron smoke 仅在非打包测试运行且显式设置 `IT_TOOLS_PLUGIN_SANDBOX_TEST=1` 时加载仓库内样例。自动化验收检查安全上下文、无 Node.js 和 preload API、插件与宿主的本地存储隔离、弹窗拒绝，以及请求到本地 HTTP 服务被阻止。单元测试覆盖插件 ID、来源、入口路径、CSP、目录绑定和文件路径边界。同一 Session 在进程内绑定一个包目录；当前没有升级流程可在运行中替换目录。该原型不安装 ZIP 包，不校验来源签名，不提供 Capability Broker，也不宣称每个插件都占用独立操作系统进程。插件清单验证和只写入暂存目录的安全安装流程仍是下一片。

`pnpm check` 通过 96 个测试文件、599 项测试、类型检查、lint 和 Web/Electron 构建。`pnpm test:e2e:electron` 的 9 项回归全部通过，其中 1 项验证沙箱原型。Electron 自动化窗口验收通过；Computer Use helper 仍无法初始化，因此没有手动控制真实桌面窗口的证据。

#### P5 第二片：签名插件包校验与安装暂存（2026-10-18）

新增 `electron/plugin-package-manifest.ts` 与 `electron/plugin-package.ts`。`plugin.json` 声明格式版本、插件 ID、版本、宿主 API 范围、HTML 入口、请求能力、按路径排序的文件 SHA-256 清单，以及 Ed25519 签名。签名覆盖除签名字段外的规范化 JSON。宿主必须提供按插件 ID 限定的受信任公钥；缺少公钥、插件 ID 不匹配或签名错误时，安装失败。请求能力只记录在清单中，不会获得授权。完整字段、签名输入与限制见[Electron 插件包格式 v1](08-electron-plugin-package-format-v1.md)。

ZIP 使用 `yauzl` 3.4.0 按条目顺序读取。安装器拒绝超过 64 MiB 的压缩包、128 MiB 的展开总量、每个 16 MiB 的资源、1 MiB 的清单、512 个文件、1,024 个归档条目，以及超过 100:1 的单文件压缩比。安装器还拒绝加密条目、路径越界、符号链接与特殊文件、NTFS 重解析点、重复或大小写冲突路径、Windows 保留名称，以及未列入签名清单的文件。每个文件流入随机暂存目录时重新计算 SHA-256。所有文件通过后，安装器才把暂存目录原子改名到插件 ID 与版本目录；已安装版本不会被覆盖。失败时删除本次暂存目录。流程只写入静态资源，不执行包内脚本或 `npm install`。

`electron/plugin-package.test.ts` 有 8 项测试，覆盖签名信任、API 兼容、篡改文件、未列出文件、Zip Slip、符号链接、重复与大小写冲突路径、压缩比、安装目录符号链接、已安装版本保护和压缩包大小限制。本片只提供可供宿主调用的校验与暂存服务；生产公钥目录、安装 UI 与激活流程仍未实现。下一片建立受宿主管理的能力授权与受限消息边界，并将其接入沙箱原型。

#### P5 第三片：受限 Electron 能力代理原型（2026-10-18）

新增 `electron/plugin-capability-broker.ts`，在插件独立来源内提供 `POST /__it_tools/v1/call`。宿主分别传入插件声明的请求能力与宿主授予的能力；代理只执行两者交集内且通过固定参数结构校验的操作。当前协议支持 `runtime.info` 读取和 `clipboard.write` 文本写入。请求和响应上限各为 16 KiB，每分钟最多 30 次，同时最多执行 4 项调用；插件窗口关闭时撤销授权，并让仍在运行的调用返回停用结果。沙箱只允许主框架通过同源入口发起请求，外部网络仍被阻止。接口与边界见 [Electron 插件能力 API v1 原型](09-electron-plugin-capability-api-v1.md)。

样例只获准读取运行时信息；剪贴板请求被宿主拒绝，因此不会改动系统剪贴板。该实现还没有连接签名包的安装、启用、停用和升级流程，也没有生产授权 UI 或 Web 能力降级，不表示第三方插件已适合公开分发。

同一片修复了关闭沙箱窗口时的 Electron 崩溃：关闭监听器现在使用窗口销毁前保存的 `webContents.id`，不再读取已销毁对象。类型检查、20 项能力代理与沙箱单测、Electron 沙箱 E2E、Electron 生产构建均通过；Computer Use 真实窗口关闭沙箱后没有出现错误弹窗。

#### P5 第四片：签名包生命周期服务（2026-10-18）

新增 `electron/plugin-lifecycle.ts`。服务通过签名包安装器将包安全暂存，读取已安装清单，并在启用前重新验证签名、目录结构和每个文件的 SHA-256。验证拒绝符号链接、硬链接、特殊文件、未列出文件及目录越界。安装最多保留 128 个插件版本；同时最多打开 4 个插件窗口。

服务支持按版本启用、停用和卸载。同一插件最多运行一个版本。启用新版本失败时，服务会重新验证并恢复此前运行的版本。沙箱入口加载最多等待 15 秒；Electron 报告窗口持续无响应 10 秒后，宿主会销毁该窗口。停用和卸载也会强制销毁活动窗口，再等待 `closed` 事件；窗口未在 5 秒内关闭时操作失败。卸载只删除规范安装根目录内指定的插件版本目录。能力授权只在当前运行会话有效；服务不会自动重启已安装插件。

`electron/plugin-lifecycle.test.ts` 覆盖签名暂存、启用前文件复核、能力授权、活动窗口限制、无响应窗口终止、版本激活失败回退和定向卸载。类型检查、4 个插件测试文件共 28 项测试和定向 lint 通过。该服务尚未接入主进程 IPC 或设置界面；宿主仍没有生产公钥或本地公钥管理流程。完整职责与限制见 [Electron 插件生命周期服务 v1](10-electron-plugin-lifecycle-v1.md)。下一片提供受信任签名密钥管理和桌面插件管理界面，再把生命周期服务接入主进程。

#### P5 第五片：签名信任、桌面管理界面与主进程 IPC（2026-10-18）

新增 `electron/plugin-trust-store.ts`，把用户信任的 Ed25519 公钥、密钥 ID 和插件 ID 允许列表保存在 `<userData>/plugins/trusted-keys.json`。信任存储只保存公钥，并以原子替换更新。读取会拒绝符号链接、硬链接、错误格式和超限文件。界面先显示 SHA-256 指纹；用户还要通过系统确认对话框完成信任。信任签名者不会自动授予插件系统能力。

新增 `electron/plugin-ipc.ts`，并将插件生命周期服务接入 Electron 主进程。IPC 只接受主框架和受信任应用来源。安装使用系统文件选择器，渲染器不会接收本机包路径。启用插件时，用户在设置页选择能力，主进程对选中能力再次显示确认。撤销签名密钥前，主进程先停用该密钥签名的活动插件。插件仍只获得 `runtime.info` 和 `clipboard.write` 两种已实现能力；其他请求保持未授权。

全局 `/settings` 页的“Electron 插件包”区显示插件包和签名者管理界面。用户可以查看安装版本、启用、停用、切换旧版本和卸载。旧 `/settings/extensions` 地址会重定向到全局设置页。Web 页面显示外部插件包仅支持 Electron，不调用桌面管理 IPC。

验证：`electron/plugin-trust-store.test.ts` 与插件生命周期单测覆盖密钥格式、指纹确认、持久化、撤销和活动窗口停止。插件 IPC 来源检查拆到 `electron/plugin-ipc-security.ts`；新增单测确认只接受受信任主框架，并拒绝子框架、插件来源、仿冒来源和空框架。6 个插件测试文件共 37 项测试、Electron 类型检查、定向 lint 和 Electron 构建通过。Electron smoke 检查受信任页面可通过 IPC 读取插件与签名者列表；Web E2E 检查桌面专属提示。真实窗口的插件信任、能力授权和安装流程仍需 Computer Use 验收。仓库没有生产签名密钥或受维护的签名插件包。

#### P5 第六片：签名包制作工具与本地插件 MVP（2026-10-18）

新增 `scripts/plugin-pack.mjs`，提供 `pnpm run plugin:keygen` 和 `pnpm run plugin:pack`。密钥生成器拒绝仓库内路径、链接和覆盖已有文件。打包器只读取静态文件，不运行插件代码或安装脚本。它验证源码清单、宿主 API 范围、能力名称、路径和资源上限，生成确定性未压缩 ZIP，并用 Ed25519 签名文件哈希清单。CRC-32、固定 ZIP 日期、签名、哈希、密钥路径、覆盖保护和 API 兼容有专项回归测试。

新增维护样例 `plugins/capability-demo/` 和[插件 MVP 快速开始](11-electron-plugin-mvp-quickstart.md)。样例通过能力代理读取运行时信息，并在用户按下按钮且授权后复制文本。插件 E2E 使用真实打包器生成签名版本，检查拒绝和批准能力、剪贴板写入、升级失败恢复旧版、停用、撤销签名者和卸载。测试在 Electron 进程内记录剪贴板写入，不修改系统剪贴板。

为限制无界计算，插件 CSP 现在设置 `worker-src 'none'`。当前不支持插件 Worker；重新开放前必须补充每插件 Worker 数量和生命周期限制。Web 与 Docker 不加载外部 `.itplugin` 包；本片也不提供商店、网络代理、生产签名者清单或自动更新。

验证：本片结束时 `pnpm check` 通过 101 个测试文件和 633 项单元测试，并完成 Web 与 Electron 构建；后续新增的打包器专项测试 5 项通过。Electron 管理器和沙箱 E2E 各 1 项通过，Electron 类型检查与 lint 通过。自动化替换了系统对话框结果；没有人工真实窗口证据。Linux/macOS 隔离、自然发生的 Chromium 崩溃和真实签名者发布仍待后续验收。

## 性能验收与 CI 演进

| 指标 | 实施目标 | 验收方式 |
| --- | --- | --- |
| 应用壳、首屏和工具体积 | 沿用 8 MiB / 300 KiB / 500 KiB 预算 | 确定性构建报告，达到目标后超限直接失败 |
| 桌面启动 | P0 基线后，以同环境中位数改善 20% 作为候选目标；p95 不回退超过 5% | P0 复核目标可行性，再在固定机器验收，不用不稳定的共享 runner 数字代替 |
| 轻量工具切换 | 已加载页面下 p95 200 ms 以内，作为待测目标 | 记录从用户动作到页面可交互；重型工具初始化与计算另列 |
| 界面响应与取消 | 代表重任务执行中仍能操作导航；取消后停止计算且不显示旧结果 | 真实窗口操作、任务状态断言和性能跟踪联合验证 |
| 内存与空闲 CPU | P0 后制定各平台预算，切换与停用后没有持续资源累积 | 整个应用进程组、堆快照与资源计数；一次内存回落不等于无泄漏 |
| 扩展成本 | 新工具不改宿主核心；闲置工具包不运行实现代码 | 生成器样例、注册检查、网络记录与生命周期测试 |

每份性能报告保留运行环境与输入规模。先对比同机同版本的重复结果，再决定是否阻止合并；对噪声大的运行时指标先报告，确认稳定后才加入 CI 失败条件。

现有验证命令按变更范围选择：

- `pnpm check`：类型、lint、单元测试、Web/Electron 构建和现有脚本检查。
- `pnpm test:e2e`：生产 Web 的三浏览器流程；PWA 定向入口为 `pnpm test:e2e src/pwa-cache.e2e.spec.ts`。
- `pnpm test:e2e:electron`：已构建桌面的 smoke；原生 runner 负责各平台打包和回归。
- `pnpm headers:docker`：需要验证 Docker Nginx 时，仅连接本地 Docker，并记录镜像、端口与清理结果。
- `pnpm perf:baseline -- --runs 20 --platform all --output docs/performance-baseline-YYYY-MM-DD-main.json`：正式桌面基线使用当前平台的 electron-builder 解包应用，Web 使用生产构建；Electron 每轮使用独立用户目录。先为当前提交运行 `electron-builder --dir`。该自动化测量不代替真实窗口验收。
- 可选参数 `--electron-app-dir .` 会改用当前 `electron-vite` 输出和本地 Electron 运行时。`out/` 必须由 `pnpm electron:build` 生成。此模式用于开发构建对照，不替代正式打包基线。
